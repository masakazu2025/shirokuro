2つの現場のやり方を、1つの仕組みにする。

背景

2つの現場のやり方

同じ「取引を探す」でも、目的によって理想の使い方が正反対だった。

閲覧特化

①自分のツール

  • IP単一・日付・取引番号で検索
  • 「最新の取引」を番号を知らずに探せる
  • 裏で自動採取、後からゆっくり整理できる

難点: 不要なもの(画像等)も採取してしまう

採取特化

②別担当者のツール

  • IP複数・現在時刻からN秒遡って一括取得
  • 取引直後に即採取するワークフロー
  • 必要なものだけ確実に採れる

難点: 閲覧性を犠牲にしている

shirokuroの検索機能 = 良いとこ取り

閲覧のしやすさは①のまま、②の即時性・確実性も取り込む

気づき

5つの条件は、2つの役割に分かれる

「よく使う/たまに使う」ではなく、「何を特定するための情報か」で条件を整理し直した。

端末を特定する
店番号どの店舗か レジNoどのレジか IPアドレス現環境では店番号・レジNoとほぼ一意
取引を特定する
日時いつの取引か 取引番号何番目の取引か

この整理により、「店番号・レジNo・取引番号をまとめて詳細検索に隠す」という当初案から、「端末はまとめて1つの選択UIに、日時と取引番号はそれぞれの性質に合った見せ方に」という、より筋の通った構成に変わった。

画面イメージ

常時表示の検索バー + 一覧

端末選択と日時は画面上部に固定。取引番号は複数端末選択時に自動でグレーアウトする。

取引 No.1041NEW10.0.0.1

自動更新は「最後に見た取引以降だけ」を取得するので、NEW表示は追加の仕組みなしで実現できる。一覧のページ送りもブラウザ内の処理だけで完結し、サーバーへの追加リクエストは発生しない。
