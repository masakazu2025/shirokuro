# 検索機能

## 背景

社内で実際に使われている2つのツールの使い方を統合することを目指す。

- **①閲覧特化(自分が使用)**: IP単一+日付+取引番号で検索。最新の取引を番号を知らなくても探せる。POS取引終了後に「最新」ボタンを連打して確認する使い方。自動採取が裏で動くため後からゆっくり整理できるが、不要なもの(画像等)も採取してしまうのが難点
- **②採取特化(別の担当者が使用)**: IP複数+現在時刻からN秒遡って、ヒットしたものをすべて取得。取引直後に即採取する使い方(スライダーで秒数指定、常時表示)。閲覧性を犠牲にしているが、必要なものだけ確実に採れる

①を採用しつつ、②の即時性・確実性も取り込む「良いとこ取り」が方針。

## 最終系(ゴール)

### 端末選択
- 店舗で絞り込んでからレジNoを選択できる、階層的な選び方(理想形)
- POS店舗サーバのレジマスタから現在の情報を取得・登録する仕組み(将来検討)
- ドロップダウン+チェックボックスで複数選択。IPを主に表示、レジNoは補足情報として表示
- ドロップダウン最下部に「詳細指定」→モーダルで自由入力のIP・レジNo指定(未登録端末や、過去のレジNo変更への対応)
- 端末を1つも選択していない場合は検索不可(空検索・巨大な結果セットの事故防止)。検索ボタンを無効化する(空状態メッセージは表示タイミングによりレイアウトが崩れる問題があったため廃止)

### 日時
- デフォルトは単一の日付(今日)。「今日」ボタンで即リセットできる
- 「詳細検索」ボタンを押すと、下に日時範囲(from〜to)の入力が追加表示される(単一入力の置き換えではなく追加。開いている間は単一入力をグレーアウトし、どちらが有効か見た目で示す)
- 展開した状態は📌固定ボタンでlocalStorageに保存し、次回も展開した状態で開ける
- 「直近N秒」(②向け、スライダー・常時表示)は将来追加。追加時も「範囲入力にショートカットで値を埋める」という同じ仕組みで追加できるため、構造を変える必要はない

### 取引番号
- 日時と同様、デフォルトは単一入力(完全一致)。「詳細検索」を開くと下に範囲(from〜to)が追加表示される
- 複数端末選択時もグレーアウトしない。入力すれば選択中の全端末に対してその取引番号(範囲)で絞り込む。レジごとに番号体系が異なるため意図した結果にならないこともあるが、それは利用者の判断に委ねる(入力できないと原因が分かりにくいUXの方が問題と判断し、当初の「複数端末選択時はグレーアウト」方針から変更)

### 検索結果
- 自動更新: 検索条件全体(端末選択含む)が前回と同一なら差分取得(最後に見た`created_at`以降)、条件が変われば全件取り直し
- NEW表示: 差分取得の結果はすべて新着なので、追加の比較ロジックなしで実現できる
- 並び替え: フロント側で保持している配列をソートするだけ(バックエンドの`ORDER BY`は不要)
- ページネーション: フロントのメモリ内配列をスライスして描画。バックエンドへの追加リクエストは発生しない
- バックエンドの安全弁(上限10000件)に達した場合は、一覧を描画せず「絞り込んでください」のメッセージを表示

### 状態の持ち方
- 好み(モード)の記憶: 日時の展開状態、クイック指定のモード → localStorage(端末・ブラウザに紐づく好みなので)
- 実際の検索値: URLクエリパラメータ(画面遷移をしても検索状態が失われないようにするため。取引データ画面⇄画像データ画面の行き来が多いため重要)

## 実装ステップ

### バックエンド
- ✅ 完了(`feature/search`ブランチ): 検索クエリの拡張、10000件上限

### 今回実装
画面レイアウトはモックアップで検証済み。フィールドの並び順は **端末 → 日付 → 取引番号 → 検索 → 詳細検索**。

- 端末選択UI: 既存の`GET /transactions`(無条件)を1回叩き、返ってきたデータから店番号・レジNo・IPの組み合わせをフロント側で重複排除してドロップダウンの候補にする(チェックボックスで複数選択、IPを主表示・店/レジは補足)。新規バックエンドエンドポイントは不要(初回デモでは`Terminal`テーブルは使わない)
- 日付: 単一入力がデフォルト(「今日」ボタンで即リセット)
- 取引番号: 単一入力がデフォルト(完全一致)
- 「詳細検索」ボタン: 押すと下に日時範囲・取引番号範囲の入力を追加表示(単一入力は自動でグレーアウト)。📌固定ボタンで展開状態をlocalStorageに保存し、次回も維持する
- 複数端末選択時も取引番号の入力欄はグレーアウトしない(グレーアウトしていると原因が分かりにくいため、入力自体は常に許可し、検索条件にそのまま使う)
- 端末を1つも選択していない場合は検索ボタンを無効化する
- 検索実行: 選択した端末・日付(または日時範囲)・取引番号(または範囲)をクエリパラメータに変換して`GET /transactions`を呼び出し、既存の[TransactionList](../frontend/src/components/TransactionList.jsx)に結果を表示
- 検索条件の状態は1箇所のフックにまとめて管理する(URL同期を今回はやらないが、後から追加するときに他のコンポーネントを触らずに済むようにするため)

### 以降実装(理由つきで保留)
- **URL⇔検索状態の同期**: 動機は「取引データ画面⇔画像データ画面の行き来」だが、`docs/現行ツール概要.md`に明記の通りポートフォリオ版には画像データ画面自体が未実装のため、優先度を下げる。画像データ画面を作るタイミングで再検討
- **ページネーション**: デモデータが20件程度で1画面に収まるため、当面不要。件数が増えたら追加
- **自動更新・差分取得・NEW表示**: デモデータは静的なので効果を体感できない。実データ接続後に着手
- **直近N秒スライダー・即検索**: ②(採取特化)向けの機能。①の実装を妨げない範囲で後回し
- **端末詳細指定モーダル**: 自由入力のIP・レジNo指定(未登録端末や過去のレジNo変更への対応)
- **店舗→レジの階層選択・POS店舗サーバのレジマスタ連携**: 将来検討
- **端末選択(localStorage保存)の整合性チェック**: 現状、端末候補は`Transaction`の実データから動的に集計しているため(`Terminal`テーブルは未使用)、一度でも取引した端末は候補から消えず、localStorageに保存した選択が無効になるケースは実運用ではほぼ発生しない。ただしデモデータの作り直し等でIP構成が変わると、保存された選択が実在しない候補を指す状態になりうる(トリガー表示とチェックボックスが食い違う)。`Terminal`テーブルを使った正式な端末管理を実装する際は、保存済みの選択が現在のマスタに存在するかを検証する仕組みを合わせて設計すること
- **日付と取引番号の詳細/単体を個別に切り替え**: 現状は「詳細検索」1つのトグルで日付・取引番号の単体入力が両方まとめてグレーアウトされ、範囲入力に置き換わる。そのため「日付は範囲で絞りつつ、取引番号は特定の1件を探す」という使い方は、範囲入力の開始・終了に同じ値を入れることで代替はできるが専用の単一入力は使えない。個別トグル化も可能だが、`detailOpen`が単一booleanから項目ごとの状態に分かれ、グレーアウト判定のロジックも増えるため、費用対効果を見て優先度は低いと判断し保留
